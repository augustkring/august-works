## 1. Method and how to read this

Status key (the brief's beta gate, 47.2, needs D2 system-tested evidence for first value, EN/DA, accessibility):

| Status | Meaning |
|---|---|
| Covered | Real backend round trip, EN and DA, accessibility asserted |
| Partial | Some real-backend or some mocked coverage; the missing piece is named |
| Mocked-only | Browser runs the real built UI, but the feature endpoints are `page.route` fixtures |
| None | No e2e spec found (UI unit tests may exist) |

Facts that shape every row:

1. Most `aw-v9-*` specs are mocked-feature specs. Pattern: real browser, real session, a real disposable company created by `request.post("/api/companies")`, then the feature endpoints are `page.route(...)` fixtures. The spec headers say so ("explicit software fixtures", e.g. `tests/e2e/aw-v9-first-value.spec.ts:18`, `aw-v9-first-task.spec.ts:12-14`, `aw-v9-auth-language.spec.ts:10-11`). The headers defer authority to "PostgreSQL suites" (server tests). So these prove UI states and keyboard/axe behaviour, not the journey.
2. Accessibility: 64 spec files call `axe.run` (axe-core injected with `addScriptTag`, for example `aw-v9-first-value.spec.ts:72-81`, `aw-v9-canonical-surfaces.spec.ts:4-8`). Almost all are the mocked specs. No UI unit test uses axe. Most real-backend specs use role-based locators only.
3. Danish: only specs that set `locale: "da"` or select Danish exercise DA (about 43 files, listed per row). `registerEnglishAccountLocaleIsolation` (`tests/e2e/account-locale-isolation.ts`) only resets the account to EN around a test; it is not DA coverage. Real-backend AND DA specs are few: `aw-v10-support.spec.ts:192-215`, `aw-v9-language.spec.ts`, `aw-v9-agent-pause-policy.spec.ts`, `aw-v9-agent-task-proposal.spec.ts`, `aw-v9-memory-maintenance-history.spec.ts`. UI unit tests with Danish: `Search.test.tsx`, `CustomerHelpCenter.test.tsx`, `SaasDeletion.test.tsx`, `Auth.test.tsx`, `CustomAgent.test.tsx`. Key parity of the two locale files is checked in `ui/src/i18n/locale-validation.test.ts`, which proves keys exist, not that the screens read well.
4. What CI runs: `pnpm test:e2e` runs `tests/e2e/playwright.config.ts` plus `aw-v10-agent-chat.config.ts` (`scripts/e2e-runner.mjs:23-25`). The default config ignores `aw-v10-support`, `aw-v10-native-auth`, `aw-v5/v7-authenticated`, `multi-user*`, `agent-chat-*`, `aw-v9-storybook` (`tests/e2e/playwright.config.ts` `testIgnore`). `aw-v4-verification.yml:579-589` runs the v5, v7, v10-native-auth and v10-support configs. No workflow reference was found for `multi-user.spec.ts` or `multi-user-authenticated.spec.ts` (only the `package.json` script `test:e2e:multiuser-authenticated`), so invitation coverage may not run in CI.
5. Provider boundary: the live-runner journeys use deterministic fixtures for the model and MCP provider (`tests/e2e/execution-recovery/recovery.spec.ts:8-9`); `tests/release-smoke/docker-auth-onboarding.spec.ts:11-27` uses a mock Anthropic endpoint inside the harness. No spec uses a real model key, Paddle, an email provider, Slack or Teams.

## 7. Caveats

- Counts rest on reading headers, titles and grep counts, not on running tests. A spec marked mocked may still hit some real routes (hybrids are noted as Mixed).
- Server (`server/src/__tests__`) and DB tests are out of scope here; the v9 specs defer authority to them, so some behaviour is covered below the browser layer. This map answers only whether the browser journey is proven.
- `tests/e2e/smoke-lab*`, `tests/runner-e2e`, `tests/storybook-visual` and `tests/lifecycle-baseline` were not mapped to journeys; they are runner, visual and accounting suites.
