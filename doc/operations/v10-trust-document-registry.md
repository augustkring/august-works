# Trust document registry and acceptance

The Trust document API is a company scoped projection over the existing immutable `documents` / `document_revisions` owner. Registry rows contain lifecycle metadata and exact revision references; they do not copy document bodies or establish certifications, hosting facts, subprocessors, or legal text.

## Current unconfigured state

No company document is registered by migration or seed. A company with no eligible registry entries receives `{ "configured": false, "documents": [] }`. A company owner or administrator registers an exact current document revision and selects its material-change action. No default legal text, effective fact, entity, region, or contract status is supplied by the product.

## API

All routes require a current Board Human identity, current account binding (`expectedUserId`), and company access. The registry checks the provider session and company membership rows again in its transaction, rejects account-deletion markers and stale authenticator generations, and does not impose recent-authentication or native-MFA proof. A current legacy or SSO session with no native proof is accepted while the account remains at authenticator generation zero; a credential lifecycle change invalidates a proof-cleared session. The registry read route returns only entries marked public, with no NDA requirement, an effective date, a review date, no superseding entry, and no elapsed expiry. It returns metadata only. Gated and internal entries are not advertised; their NDA flag does not grant body access.

`GET /api/companies/{companyId}/trust/documents?expectedUserId={userId}` returns the eligible projection. Each read also rechecks that the referenced revision remains the document's latest revision, was authored by its recorded Human owner, has no retained source dependencies, and remains unattached to private owner records. It withholds documents with document-level source-trust metadata and revisions referenced by Foundation sections or change proposals. A newly linked or changed source is withheld without waiting for a registry rewrite.

`GET /api/companies/{companyId}/trust/documents/{registryEntryId}/content?expectedUserId={userId}` returns the exact canonical body and format for any current public entry that passes the live revision, privacy, source, session, company-status, and membership checks. The returned metadata identifies the exact revision/version to review. This route never returns gated or internal content.

`POST /api/companies/{companyId}/trust/documents` is restricted to a current authenticated company owner or administrator. It accepts an exact current native document revision and effective/review/expiry metadata, evidence references, visibility, NDA flag, review trigger, and one owner-declared `materialChangeAction`: `notice`, `reacceptance`, `customer_admin_acknowledgment`, or `no_action`. Registration rechecks the current session and membership in the write transaction, and requires the registering Human to have created and last updated the standalone company document and exact revision, without agent or run authorship. Documents attached to issues, cases, pipelines, routines, Foundation, Playbooks, Status Cards, Summary Slots or annotation threads, and revisions with retained source dependencies, are not publishable through this projection. The authenticated principal is the recorded owner; a new revision supersedes prior registered entries for that native document. The document revision number is the canonical displayed version.

The legacy `acceptanceRequired` input remains accepted: `true` maps to `reacceptance`, and `false` maps to `no_action`. Existing rows migrate with the same mapping. When `materialChangeAction` is supplied, the legacy projection must agree (`acceptanceRequired` is true only for `reacceptance`). A material action is declared per registered version; the product does not infer legal materiality from document-body differences.

`notice` creates an action-required notice that the current Human can explicitly mark read at `POST /api/companies/{companyId}/trust/notices/read`; that receipt is per Human and exact version. `reacceptance` requires the existing explicit acceptance route and receipt per Human and exact version. `customer_admin_acknowledgment` remains visible until a current company owner or administrator records an acknowledgment at `POST /api/companies/{companyId}/trust/admin-acknowledgments`; one valid acknowledgment completes that exact company version. `no_action` creates no action-required notice or completion receipt. All completions bind the exact registry row, revision, and version. A later registered revision starts a separate requirement. These actions do not establish consent to a privacy disclosure or optional data use.

`POST /api/companies/{companyId}/trust/acceptances` requires an authenticated session and records an explicit user action for one currently eligible, public, reviewed, unexpired registry entry whose exact version has `materialChangeAction: "reacceptance"`. It repeats the same current-revision and source-scope check under row locks before creating an acceptance. The request includes `expectedUserId`, a UUID `requestId`, `registryEntryId`, exact `version`, and `surface`. The database stores the authenticated principal and organization, exact revision/version, request fingerprint, acceptance surface and server timestamp. A matching retry returns the original receipt; reusing the key for different terms fails. Acceptance rows cannot be edited or directly deleted; company erasure cascades its company-scoped acceptance evidence. Notice-read and administrator-acknowledgment receipts are separately typed and append-only.

## Gated assurance access

Gated registry metadata and content use separate routes from the public projection. Public list/content responses never include gated rows, titles, or bodies. The gated list requires a current Human company membership. A current company owner or administrator can see eligible gated metadata and whether a grant is required. A Human with an active grant sees only the exact granted entry. The list returns `canGrant` from the current membership role; it is not a grant itself.

`GET /api/companies/{companyId}/trust/gated/documents?expectedUserId={userId}` returns only current, reviewed, effective, unexpired, unsuperseded gated documents that still meet the same standalone Human ownership, source-free, no-private-association, non-invalidated, and non-erased rules. An owner or administrator may see `access.state: "grant_required"` and issue an explicit grant. An eligible document with `ndaRequired: true` is shown to current administrators only with `access.state: "nda_binding_unconfigured"`, `requiredBindingOwner: "canonical_nda_agreement"`, and `receiptReference: null`. The condition records that no canonical binding owner or receipt exists; it is not evidence of an NDA or permission to read the body.

`POST /api/companies/{companyId}/trust/gated/grants` requires a current owner or administrator. It grants one exact `registryEntryId` and `version` to a named existing active company Human, and requires an explicit future `expiresAt`, UUID `requestId`, and `surface`. The registry row and native revision must still be current and eligible in the transaction. A matching retry returns the original immutable grant receipt; reuse of the request key with different terms fails. Granting access does not change document source permissions. Administrators must grant themselves explicitly before opening a document in Help → Trust Center; the current Help surface asks for expiry and does not auto-open content after grant.

`GET /api/companies/{companyId}/trust/gated/documents/{registryEntryId}/content?expectedUserId={userId}&grantReceiptId={grantId}` returns a body only for the actual current Human holding that exact, unexpired, unrevoked grant. It rechecks current company/session membership, registry version, latest revision, review/effective/expiry/supersession, document source/privacy state, source erasure markers, and the grant under row locks before returning the canonical revision. The Help surface requires a separate explicit “Review current document” action and offers download only after that response arrives. Its no-store requests and query cache are scoped to company, account, and session and are cleared on those changes or when the Help view is left.

`POST /api/companies/{companyId}/trust/gated/grants/{grantReceiptId}/revoke` revokes one exact grant. Only a current company owner or administrator can revoke. The grant and the separate revocation receipt are append-only; later reads fail when the grant is revoked, expired, superseded, or the document acquires a private owner association or source. Grant expiry is explicit and required.

There is no canonical NDA agreement, approved NDA text, signed-party record, or NDA execution receipt configured in this product. Therefore `ndaRequired: true` fails closed: the gated list reports the typed unconfigured state and a grant attempt returns `trust_nda_binding_unconfigured` with a null receipt reference. The generic document acceptance receipt is not an NDA execution and cannot unlock these bodies. NDA access remains unavailable until a canonical agreement/binding owner and its actual approved terms and receipt semantics exist.

Privacy notices are not converted into consent. Marketing and optional data-sharing consent have no representation in this registry or acceptance API. Legal owners remain responsible for deciding whether document changes require notice, re-acceptance, acknowledgment, or no action.
