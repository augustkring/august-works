# August Works V7 native OpenShell host control

Date: 2026-10-05. This extends the existing V6 native host protocol; it does not authorize deployment or physical workload admission.

## Native integration

The SaaS platform registers the OpenShell backend when both `AW_RUNTIME_OPENSHELL_PROVER_PATH` and `AW_RUNTIME_OPENSHELL_PROVER_SHA256` are configured. The path must be absolute; the existing prover adapter verifies the executable bytes against that digest before each proof. Do not use a Task argument, request body or model-generated path for either value.

Host-agent 6.0.1 adds an OpenShell command lane to the existing `runtime_host_commands` table. Host-agent 6.0.2 adds immutable instance pinning. The server requires 6.0.2 before it queues or accepts sandbox commands. The original host claim endpoint selects only the original runtime command types. Signed POST requests to `/api/internal/runtime/hosts/:hostId/sandbox-commands/claim` and `/sandbox-commands/:commandId/complete` use the existing RSA request proof, credential epoch, nonce and raw-body authentication. Commands use the existing RSA-OAEP/AES-GCM envelope. No reusable provider credential is included.

Every operation pins the company, sandbox binding, native cell, generation, deterministic `aw-v7-<binding UUID>` name, image configuration, host and credential epoch. Native membership/permission and V7 flags are checked again at non-safety claim, completion and receipt consumption. Scope changes cancel pending work. Stop, provider revocation and destruction remain available after rollout rollback; enqueue still requires a current human runtime manager. The existing autonomous sandbox guardian separately uses its system-attributed native Stop path. Neither path impersonates a revoked user.

The host row serializes admission against the bounded queue capacity. Commands have a finite deadline, at most three claims and a bounded lease. Cleanup expires abandoned commands. Results are strict bounded action-specific records, with immutable completed receipts and native audit events. Concurrent requests with the same safety operation key share one command. A persisted command receipt is distinct from a runtime operation row and distinct from complete sandbox qualification.

## Private host CLI configuration

The operator's private host configuration may include `openshellCli` with `executable`, `executableSha256`, `gateway`, `workspace`, `stateHome`, `policyProverExecutable`, `policyProverSha256`, `policyProofDockerExecutable`, `policyProofDockerSha256`, `policyProofScratchHome` and `policyProofScratchCapacityBytes`. It selects an existing authenticated OpenShell gateway by explicit name and workspace. Keep the CLI state directory private to the host-agent user, with no group/other permissions. The executable must belong to that user, be executable, have no group/other write permission and match the configured digest. The host checks these conditions and actual `openshell 0.1.2` version before CLI observations or effects.

The operator supplies the fixed `openshell-prover` 0.1.2 executable and its SHA-256 in `policyProverExecutable` and `policyProverSha256`; these are deployment pins, never command fields. The operator also pins the absolute Docker CLI path and SHA-256 in `policyProofDockerExecutable` and `policyProofDockerSha256`; proof operations use that executable. `policyProofScratchHome` must be the root of a dedicated tmpfs mount with the exact configured `policyProofScratchCapacityBytes` (768 MiB), a host-agent-owned mode-0700 directory, and at least 736 MiB free before proof. The Host checks the mount type and size, directory owner/device/inode, free space, executable owner/mode and digests, and Docker CLI version (20.10.24 or newer) before copying data. Proof commands share the Host's serialized command queue. The Host image includes `/usr/bin/getfattr`; absence or an unreadable overlay audit fails the proof. Keep provider credentials out of this configuration.

The Host proves only an exact stopped sandbox. It copies the merged TaskRoot, `/.openshell/runtime`, and each relevant mounted guest root from the pinned stopped container using the Docker CLI's archive-copy path into the capped tmpfs scratch, preserves ownership, and rejects external symlinks/hardlinks, special nodes, size/count overruns, and relevant overlay shadowing/whiteout/xattr cases. The qualified runtime binary is byte-verified against the retained qualification sample, then copied into private scratch with mode 0555 and mounted read-only as the helper entrypoint. The exact TaskRoot projection, runtime tree, policy documents, pinned prover, bootstrap, and relevant mount snapshots are all mounted read-only from private scratch before the helper starts; no helper copy-in is used. The Host keeps these sources until owned helper cleanup, binds them into the exact workload image, and checks their contents before and after prover execution. Combined retained snapshots must fit the configured scratch cap, and each readback must fit the currently available scratch space. Every TaskRoot entry must be present in the target overlay upper layer; lower-layer TaskRoot entries are unsupported. Relevant mount snapshots are limited to 64 MiB total and never shared live with the stopped workload. A boundary root that is an ancestor of the TaskRoot is accepted only inside a private `/workspace` namespace; each directory from that root to the TaskRoot parent must be a symlink-free directory in the stopped target's overlay upper layer. Missing outer ancestors are accepted only when the same immutable image contains the expected directory and the overlay audit finds no override or whiteout. The Host recreates the private directory metadata and exact TaskRoot subtree while omitting sibling contents. It runs the pinned prover in a no-network, resource-capped helper from the exact workload image. Docker client proxy variables are explicitly cleared in that helper. The pinned prover 0.1.2 compares filesystem policy paths literally; it does not resolve path containment, so a narrower TaskRoot and ancestor boundary currently fail closed as unsupported even when both snapshots are correctly mounted. The gated software test verifies a real all-bind proof for identical path sets and the real prover's `unresolved_filesystem_path` result for a narrower TaskRoot; it does not establish nested-path containment. Private snapshots do not change the prover's path comparison rule. Any unsupported path, mount, overlay change, or helper cleanup ambiguity fails closed. The returned proof is software evidence about the exact observed policy documents and filesystem roots; it does not establish physical enforcement or qualify a workload by itself.

The subprocess receives only the private state home, a fixed system PATH, language and no-color settings. It inherits no provider keys or insecure-TLS option. Calls use argument arrays, bounded output and deadlines. Never put a credential in a CLI argument or environment field. Install the pinned CLI and its qualified gateway metadata in the private host image/configuration using the deployment process; the agent neither downloads binaries nor creates a gateway.

Existing sandboxes must have the exact native name/workspace and `aw.company_id`, `aw.binding_id`, `aw.cell_id` and `aw.generation` labels. The controller checks them before each effect. It does not create or discover arbitrary worker-selected sandboxes. The first accepted observation persists the gateway-assigned immutable sandbox UUID before any effect. Subsequent observations, revocation steps and restart fencing require the same UUID as well as the exact native scope. A reused name with copied labels cannot replace that pin. Legacy journal entries without an observed UUID remain fenced and require operator reconciliation; the controller does not fill in their identity from a current name lookup. Stop targets one sandbox and requires an observed `Stopped` phase on that same UUID. Destruction requires a bounded, complete absence observation. Provider detach uses exact observed provider names with readiness waits and a subsequent empty attachment observation; more than four attached providers or incomplete pagination remains unsupported. Stop is attempted independently when revocation fails by the existing adapter.

The private durable journal retains receipts across restart and records only validated owned scopes for host-lease fencing. Host loss attempts both the existing cell engine and OpenShell engine even if one fails. Fencing rechecks labels and never runs a gateway-wide `--all` operation. Failed or ambiguous effects require reconciliation. The upstream V0.1.2 lifecycle CLI still sends name-scoped mutation requests without an instance-ID precondition. Before/after identity checks detect drift but cannot make those upstream effects atomic against an independently concurrent recreation. This lane remains a scoped safety controller, not an earned physical workload-admission guarantee.

### Installed runtime broker profile selection

The private `openshellCli.runtimeBrokerProfiles` object optionally selects `app` and/or `model` profiles already installed in the selected authenticated gateway/workspace. Each entry has exactly `{ id, hash, origin, binaries }`: the actual installed profile identifier, SHA-256 of canonical sorted-key JSON from `profile describe`, canonical HTTPS platform origin without trailing slash, and exact array of absolute binary paths. Supply values from the operator's pinned installation artifact. There are no implicit profile names, generated profiles, automatically trusted hashes, downloads or qualification-canary defaults. Missing selection advertises no runtime broker profile. The selector contains no credentials and never comes from workload arguments.

The Host re-reads actual installed metadata on each discovery, under the existing operation deadline bounded by the original provisioning and qualification ceilings, and requires the pinned hash, role, endpoint and binary set to match. App profiles use only `PAPERCLIP_SANDBOX_BROKER_TOKEN` with bearer Authorization and one enforced HTTPS POST `/mcp/gateways/*` rule. Model profiles use only `PAPERCLIP_SANDBOX_MODEL_TOKEN` with the exact POST `/runtime-tools/model/v1/messages` rule. The qualification profile's separate `PAPERCLIP_SANDBOX_QUALIFICATION_TOKEN` cannot authorize ordinary business use. Request-time provider inspection uses the same role validator. Changes require the installed artifact/configuration to be reconciled and fresh qualification; discovery never renews a qualification expiry.

The resolver returns actual id/hash plus the profile's endpoint/binary enforcement dimensions. This metadata alone does not prove company/presence/expiry/revocation authority or passed qualification. Those remain the existing signed broker/current-run/current-grant owner and the server's complete protected nineteen-case qualification gate. It does not enable prover coverage or physical admission.

## Remaining physical controls

Protected reports are derived from the exact journaled creation, current policy and fresh Host observations; the server still requires the complete protected nineteen-case result set before qualification. CLI resource metadata and controlled software tests do not prove enforcement on a physical target, disk/PID/wall-clock behavior under stress or customer credential isolation. Do not treat a protected report or a local injected-CLI pass as physical qualification.

Local PostgreSQL and injected CLI tests cover actual native queue, authorization, encryption, drift, cancellation, replay, unsupported qualification, private configuration and scoped effects. They are fixtures, not protected physical or live-customer evidence. The integrated pilot manifest therefore retains the OpenShell implementation blocker. Complete the outer enforcement and credential-use broker before attempting a managed workload on qualified staging.
