# V7 internal Agent Package evaluation

Date: 2026-10-05. Local implementation protocol; no customer launch or physical-isolation attestation.

`INTERNAL_SOURCE_REVIEW_ROLE_ITEMS` and `internalSourceReviewRelease()` in the shared package define the shipped internal distribution. They compose typed native execution policies. The customer-facing catalog contains only explicitly published releases; this helper does not seed or approve production evidence.

1. A current company operator creates and publishes the internal Role Pack through its native API. Compute its semantic digest with `aw_v7_package_component_hash(company_id, 'role_pack', role_pack_id, role_pack_version_id)`. The digest deliberately excludes tenant UUIDs and administrative revision labels; it includes ordered typed policy content. Equivalent resources in another company resolve independently through that company's current access checks.
2. A configured first-party publisher supplies the actual build commit, exact component/source versions and protected release-authorization/provenance artifact references to the shared helper. Publish using `POST /api/agent-packages/releases`. Ordinary company administrators and agents cannot publish. Signed evidence, SBOMs, vulnerability scans, evaluations and holdouts remain separate dimensions; missing evidence is never synthesized by this flow.
3. Through Agents → Specialist packages, select an existing native presence, the exact matching approved component version, and acknowledge internal evaluation. Preview records native knowledge/readiness observations. Install pins the agent's native Role Pack and creates no permission, subscription or connection grant.
4. Configure/qualify the existing runtime and grant any needed source/connection access explicitly through the owning native UI. Activation checks the current human/worker intersection, source knowledge, provider conformance, component digests, commercial product where required and intended purpose. Internal evaluation allows governed read tools. BYO host enforcement remains the customer's stated responsibility; read-tool policy does not attest physical filesystem/network isolation.
5. Updates require a new immutable release. Material purpose/policy/component changes require explicit review, and saved configuration requires separate activation. `auto_low_risk` is a stored company policy for the forthcoming bounded stewardship consumer; no autonomous material update is enabled by this slice. Learning proposes company-local updates to already-published releases and cannot publish a global package. Human acceptance retains original evidence lineage.
6. Revocation, source withdrawal, version drift, expired readiness or rollout rollback fence execution. Native run pins include the activation revision. A fresh activation cannot revive an old run. Durable Stop uses the existing controller with a 90-second recoverable lease and five cumulative attempts; delivery is not proof of a physically stopped host. Uninstall retains native agents, Role Packs, Work and Memory and keeps immutable installation history.

Local representative tests cover authorization/tenant negatives, no hidden grants, optional/required connection handling, native Knowledge requirements, immutable publication, stale components/authority, material updates, source erasure and restored payloads, cancellation recovery/concurrency and human activation. They do not establish customer demand, model business-output quality, cost/latency envelopes, live provider portability or managed-host qualification. Waves 16/19 require those actual artifacts before a customer specialist release.
